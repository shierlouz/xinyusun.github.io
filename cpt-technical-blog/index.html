CPT 不是把领域文本继续喂给模型那么简单。它同时改变训练分布、 输入边界、通信负载和梯度方向；任何一环失真，都会在最终模型上 表现为学习不足、能力遗忘或训练吞吐异常。

更准确地说，领域 CPT 是一个系统问题。训练目标决定模型要保留什么， 流式管线决定 GPU 实际看到了什么，分布式框架决定计算能否稳定扩展， 监控与优化算法则决定多个目标如何竞争。它们必须在同一套可观测链路里闭环。

“配置中的训练比例”只有落实为等长 token chunk 和真实 optimizer step， 才是模型实际经历的训练比例。
SYSTEM / 01

让训练管线忠实执行设计

传统方案往往先完成全量预处理，再把静态 input-id 文件交给训练器。 这种方式启动链路长，并且 tokenizer、模板、序列长度或 packing 策略任一变化， 都可能使缓存整体失效。更关键的是，静态缓存把“样本如何变成一个训练 step”隐藏了。

在线流式方案把这条链路重新暴露出来：数据通道保持独立，样本惰性读取， shuffle 在有限缓冲区中持续发生，tokenize、EOS 和 packing 在训练侧在线完成。 这样既减少中间状态，也能对每一步的来源和边界进行审计。

01Channel sampler按训练目标选择领域通道，而不是先拼成一个不可观测的数据池。
02Online tokenize在线编码、切分并显式补齐 EOS，保留真实文档边界。
03Domain packing各通道独立组包，避免不同语义域在同一序列中无边界粘连。
04Fixed chunk在等长 token chunk 上采样，让配置比例与有效更新保持一致。

为什么必须同域 Packing

Packing 的目标是减少 padding，但如果只追求填满序列，来自不同领域的文档可能被 直接拼接。即使中间有 EOS，这种随机邻接也会改变上下文分布，并让分领域监控失去解释性。 因此，每个通道需要独立维护 pack buffer，只有同域文档才能进入同一个训练序列。

trainer.pipeline
channel = sampler.next()
doc = channel.read_lazy()
tokens = tokenizer(doc) + [EOS]
chunks = packer[channel].append(tokens)

for chunk in chunks:
    assert len(chunk) == sequence_length
    trainer.consume(chunk, domain=channel.name)

OBSERVABILITY / 03

全局 Loss 会隐藏真正的问题

混合训练的全局 loss 是多个分布的聚合值。它下降，并不意味着每个领域都在有效学习； 某个目标甚至可能主导更新，而其他目标几乎停滞。训练框架至少需要按领域输出 Loss、 PPL、梯度范数，以及各领域梯度与混合梯度之间的余弦相似度。

TOKEN NLL− log P(xt | x<t)
DOMAIN LOSSΣ NLL / valid tokens
PERPLEXITYexp(domain loss)
ALIGNMENTcos(gd, gmix)

梯度范数只回答“这个领域推得有多用力”，余弦相似度则回答“它是否持续沿着最终更新方向”。 一个领域即使范数不最大，只要方向更一致，仍可能长期支配混合梯度。这也是固定采样比例 经常无法阻止能力偏移的原因。

OPTIMIZATION / 04

把遗忘改写成多目标优化问题

固定 replay 只能规定每类样本出现多少次，无法规定它们对参数更新产生多大影响。 更稳妥的抽象是：每个领域都是一个优化目标，训练器要同时控制更新幅度、学习速度与方向冲突。

SMOOTH

EMA

对历史梯度或权重做指数平滑，降低单个 batch 的方向抖动。它不解决目标冲突，但能让更新轨迹更稳定。

BALANCE

GradNorm

按各目标的相对学习速度动态调节权重。学得过快的目标降权，滞后的目标获得更多更新预算。

CONFLICT

CAGrad

在平均梯度附近寻找兼顾最差目标的方向，用显式优化处理多个领域之间的梯度冲突。

SCHEDULE

Single-domain batch

每个 step 只出现一个领域，把单步内混合改为跨 step 周期调度，减少同一步中的即时梯度干扰。

这些方法不是互相排斥的开关。EMA 处理时间维度上的噪声，GradNorm 处理学习速度失衡， CAGrad 处理同一步内的方向冲突，单领域 batch 则从调度结构上减少即时干扰。 最终选择应由分领域监控来驱动，而不是只比较一个总分。

RECOVERY / 05

断点续训不是加一个路径参数

真正可恢复的训练需要同时保存模型权重、优化器、学习率调度器、随机数状态、 consumed samples 和并行拓扑。只加载模型权重虽然能继续运行，但训练轨迹已经改变， 不能视为严格续训。

DISCOVER枚举 checkpoint只识别命名合法的 step 目录
VALIDATE校验完整性权重、状态与 tracker 必须齐全
DECIDE判断是否结束global step 与 max steps 对比
RESTORE恢复完整状态保持数据消费位置和 RNG 连续

自动恢复器需要区分三种状态：没有 checkpoint、存在可恢复 checkpoint、训练已经完成。 它应选择最新且完整的 checkpoint；发现半写入目录时跳过并报警；达到目标 step 时直接退出， 而不是再次追加 resume 参数启动训练。

FAILURE BOUNDARY

GPU UECC、CUDA launch failure 和随后的 NCCL error 通常属于同一条硬件故障链。 框架应负责定位 rank、保留最后完整 checkpoint 并支持重启，但不能把不可纠正的 ECC 错误“修复”为软件异常。

VERIFICATION / 06

转换与恢复之后，必须做等价性验证

Megatron 与 HF 之间的权重转换、断点恢复、tokenizer 更新都可能造成“模型能加载， 但行为已经改变”的隐蔽错误。验证不能止于文件存在或一次前向成功。

Tokenizer词表大小、特殊 token 与 EOS ID 完全一致CHECK
Boundary每个文档结束位置都显式插入 EOSCHECK
Packing跨文档拼接保留边界，跨领域组包符合设计CHECK

Logits固定输入下，转换前后关键位置 logits 对齐CHECK
Resume优化器、调度器、RNG 与 consumed samples 同步恢复CHECK

最有价值的测试是固定一小批输入，在转换前后比较 tokenization、首个生成 token、 关键位置 logits 和 EOS 行为。如果 tying 配置或词表映射错误，这类差异会在真正训练前暴露。

TAKEAWAYS / 08

可复用的技术结论

  1. 01
    输入边界是一等公民。

    EOS、packing 与 domain label 必须从样本贯穿到训练 step。

  2. 02
    比例要在 token 层落地。

    样本数比例无法代表真实计算量，更无法代表梯度贡献。

  3. 03
    扩卡问题要分层诊断。

    把计算、供数、节点内通信和跨节点集合通信分别测量。

  4. 04
    监控必须面向目标。

    全局 loss 之外，还要看到每个领域的速度、幅度与方向。

  5. 05
    恢复必须恢复状态。

    权重续上不等于训练续上，数据位置与随机状态同样重要。
